# foo_jl_tidal_mac — architecture and alignment review

Scope: `src/API`, `src/Core`, `src/Services`, `src/Integration`, `src/UI`, `Tests/`, `docs/` at `dev/tidal-integration` HEAD `5c92ed1`.
Findings below survived a two-verifier adversarial pass; duplicates reported under different titles have been merged.
Counts: 0 critical, 5 high, 26 medium, 21 low.

---

## 1. Verdict

The layering is sound where it matters: pure policy (HTTP status mapping, quality cascade, manifest parsing, pagination, sync planning, browser predicates) is split into Foundation-only units with 12 test suites behind them, and the fb2k SDK is mostly confined to `Integration/`. The defects cluster in the three places that policy split does *not* cover: the async seams (playlist indices captured across `process_locations_async`, a DASH blob cache keyed one level coarser than the stream cache above it), the resilience layer (there is no retry anywhere — not for 5xx, 429, network errors, or individual DASH segments — and `exception_io_data` turns every one of those into an fb2k track skip), and the response-parsing surface (`assetPresentation`, `previewReason`, `allowStreaming`, `streamReady`, `audioMode`, `replayGain`, `subStatus` have zero readers in `src/`; a single grep confirms it). The largest alignment gaps versus other clients are: no retry/backoff at all where the official Player spec mandates 3 retries at 500/1000/2000 ms; no `immersiveaudio=false` on playbackinfo, which every serious client sends; preview assets accepted as full tracks where tiddl and the official SDK reject or flag them; v1 mutations POSTed as JSON where every working client sends form-encoded; and a v2 folders request/parser pair that matches no documented response shape, so folder hierarchy has never worked. Two features are silently non-functional today (folder hierarchy, ISRC matching) and one just-shipped feature — the `?q=` quality pin — is defeated on every track after the first because the prefetcher drops the pin and the blob cache ignores it. Fix first, in order: the DASH cache key (one-line key change plus honouring `parsed->quality` in the prefetcher), the sync index-capture race (resolve by GUID or order Deletes first), preview-asset rejection, and a bounded retry in `performRequestWithURL`. Those four are cheap and each removes a class of silent wrong behaviour rather than a cosmetic issue.

## 2. Confirmed findings

### Critical

None. Nothing found corrupts user data irrecoverably, crashes at runtime outside process teardown, or exposes credentials.

### High

**H1 — Pull apply hands async imports a playlist index, then deletes playlists in the same loop and shifts it**
`src/Core/TidalPlaylistSync.mm:388` (Create), `:413` (Update), `:426` (Delete), `:606-618` (`TidalSyncImportNotify`)

`applyPullWithReport` runs the whole change list synchronously inside one `fb2k::inMainThread` block. Create captures `newIdx` from `create_playlist(..., SIZE_MAX)` and Update captures `idx` from `find_playlist`, both handed to `addTracks:` which calls `process_locations_async` — documented in `SDK/playlist.h:850` as returning immediately. Delete then calls `pm->remove_playlist(idx)` in the same loop, and `planPullPreview` appends every Delete *after* every Create/Update (`:336-348`), so the removals always execute before any import completion can be delivered to the (still busy) main thread. `on_completion` re-resolves nothing: it bounds-checks `m_playlistIndex < get_playlist_count()` and inserts by that number. The trigger is ordinary — a rename or folder move on TIDAL produces Create(new name) + Delete(old name) in one plan, because the local name embeds the folder path. Outcomes: with one Create and one Delete the new playlist is created *empty* and the tracks are dropped by the bounds check; with an Update above a deleted playlist, `playlist_clear` has already emptied the synced playlist and the tracks are appended (with `playlist_undo_backup` taken on the wrong target) to whatever playlist now occupies that index. The status bar says "Pull complete" either way.
**Fix:** capture `playlist_manager_v5::playlist_get_guid(idx)` at dispatch and `find_playlist_by_guid` in `on_completion` (skip on `SIZE_MAX`). Minimum viable: order Deletes before Creates/Updates. The same index-capture shape exists in `TidalPlayNotify` (`src/UI/TidalBrowserController.mm:93-112`) — lower risk there because the component issues no deletes in between, but worth the same fix.

**H2 — DASH blob cache is keyed by track ID only, while everything above it is keyed by (track, quality)**
`src/Integration/TidalDashCache.mm:128` and `:166`; `src/Integration/TidalPrefetch.mm:48-63`

`StreamCache` is deliberately keyed `trackID|quality` and its header says why: "A track-only key would serve one pin's stream for the other" (`src/Core/StreamCache.h:23-26`). The decoder honours the entry's pin — `resolveStream` at `TidalInputDecoder.mm:237` even carries the comment "One place decides which tier a play asks for". One layer down, `blobForTrackID:` returns `self.blobs[trackID]` without comparing `mediaTemplate`, and `ensureOpLocked` short-circuits on `self.blobs[trackID] || self.ops[trackID]`, so a second caller's template and segment count are discarded. `TidalPrefetch` compounds it: it parses the next entry, checks `parsed->type` and throws away `parsed->quality`, then resolves at the global preference. Because prefetch fires on every track change, in ordinary sequential playback the prefetch's tier wins for every pinned entry after the first, while `get_info` stamps `TIDAL_QUALITY` from the *pinned* resolve (`TidalInputDecoder.mm:539-541`). Both affected tiers are FLAC-in-fMP4, so nothing downstream rejects the mismatch. The same track-only lookup is used by `TidalLibrarySaver.mm:179`, so a wrong-tier file can be written to disk. Blobs have no TTL and `qualityChanged:` clears nothing (`TidalPreferencesController.mm:619`), so a mid-session preference change is also ignored until LRU eviction.
**Fix:** key blobs and ops on `(trackID, resolved quality)`; make `TidalPrefetch` call `resolveStreamForTrackID:quality:` with `parsed->quality` when present. Do not key on a hash of the media template — templates carry per-resolve signed tokens and replay hits would break. Add a `JLTidalDashCache` unit test for coalescing-by-key (the class is Foundation-only).

**H3 — Preview assets are accepted, cached and played as full tracks**
`src/Core/TidalModels.mm:333-382`

`JLTidalPlaybackInfo initWithDictionary:` reads `audioQuality`, `bitDepth`, `sampleRate`, `codec`, `manifestMimeType`, `manifest`, `url` and nothing else. `grep -rn "assetPresentation\|previewReason" src` returns exactly one hit — the lowercase *request* parameter at `TidalAPI.mm:405`. The response field is never read back. `decisionForPlaybackWithDirectURL:` (`StreamResolutionPolicy.mm:75-107`) accepts on `hasDirectURL || hasDASH && !drmProtected`, and the quality cascade only fires on an *error*, so an HTTP 200 carrying a PREVIEW manifest is accepted on the first try. The official OAS defines `trackPresentation [FULL, PREVIEW]` with `previewReason [FULL_REQUIRES_SUBSCRIPTION, FULL_REQUIRES_PURCHASE, FULL_REQUIRES_HIGHER_ACCESS_TIER]`, so a paying subscriber hits this on a tier-gated track, not only a lapsed one. The result is silent: `applyTrackMeta` overwrites the inner decoder's real 30 s length with `track.duration` (`TidalInputDecoder.mm:164`), so the seekbar shows 4:12 while audio stops at 0:30 and fb2k advances. The 500 KB "likely a preview clip" heuristic at `:413` is log-only and sits in the BTS branch only — the DASH/lossless path has no size check at all. The result is cached for 15 min (`StreamCache`), and a DASH preview blob until eviction, so renewing a subscription does not appear to fix playback.
**Fix:** parse `assetPresentation` (treating absent as PREVIEW, as `tidal-sdk-web` does) and `previewReason`; fail resolution with a distinct error carrying the server's message; never write such a result into `StreamCache`/`JLTidalDashCache`; and gate `TidalLibrarySaver` on it so a 30 s clip is never exported.
**Reference:** tidal-sdk-web `playback-info-resolver.ts` (`assetPresentation: …trackPresentation ?? 'PREVIEW'`), TIDAL OAS `TrackManifests_Attributes`, tiddl `TrackStream.assetPresentation: Literal["FULL"]` (a PREVIEW response raises).

**H4 — Nothing is ever retried: 5xx, 429 and network errors each become a track skip**
`src/API/TidalAPI.mm:1159` (network), `:1176-1187` (429), `:1208` (5xx via `HTTPResponsePolicy.mm:78`); `src/Integration/TidalDashCache.mm:236`; `src/Integration/TidalInputDecoder.mm:272-278`

The transport has one re-issue in the whole file, the 401 path. A transport error completes immediately as `NetworkFailure`; a 5xx completes as `Fail`; a 429 records a limiter hit and completes. `decision.retryAfterSeconds` is parsed and unit-tested but used only in the log/message string — `recordRateLimitHit` takes no argument and applies its own 1/2/4…60 s schedule, so a `Retry-After: 30` gates the next request for 1 s and re-hits the server. `StreamResolutionPolicy.mm:60-72` propagates everything except `SubscriptionRequired`, and `TidalInputDecoder` converts any resolver error into `exception_io_data` — which the code's own comment at `:357-360` describes as causing "a cascade of skip-fail-skip-fail across the playlist". `fetchAllPagesWithLimit` (`:147`) fails a whole collection on one bad page. `JLTidalErrorIsRetryable` (`TidalErrors.h:66`) has zero callers. The DASH path is worse than the API path: `assembleTrackID` discards a partially assembled 50-75 MB blob on the first failed segment GET out of dozens, with no retry and no status code returned to the caller. The design doc specified the missing behaviour verbatim (`docs/design/2026-01-07-tidal-integration.md:1300-1304`, `:1330-1334`).
**Fix:** bounded retry in `performRequestWithURL` for GET/HEAD on network errors, 5xx and 429 (3 attempts, 500/1000/2000 ms, jittered), honouring `Retry-After` by feeding it into the limiter; per-segment retry in `dashSyncGET`; have the resolver treat NetworkFailure/ServerError/RateLimited as bounded retry-same-tier rather than propagate.
**Reference:** TIDAL Player spec "HTTP error handling" (5xx/429 retried 3x at 500/1000/2000 ms, network errors retried; 4xx never); tidal-sdk-web `retry.ts` (429/5xx B=500 ms M=16 s 3 retries, network 10 retries, GET/HEAD/OPTIONS only); music-assistant `throttle_retry.py` (sleeps `max(Retry-After, exp backoff)`, 5 attempts).

**H5 — A 401 on a locally-fresh token never triggers a real refresh; the retry re-sends the rejected token**
`src/Services/TidalAuthService.mm:436-439`; `src/API/TidalAPI.mm:1190-1204`

The block installed as `JLTidalAPI.tokenRefreshHandler` (`:66-73`) is `refreshTokenIfNeededWithCompletion:`, which answers `completion(YES)` without any network call whenever `!session.needsRefresh` — a purely local check against a 300 s buffer. The 401 branch therefore re-issues the identical `Bearer` value with `isRetry:YES`, and `HTTPResponsePolicy.mm:59-66` maps the second 401 to `NotAuthenticated`. Because the pre-request check at `:1093` already handles an *expired* token, the 401 path can only ever perform a real refresh inside the 5-minute pre-expiry window; outside it the log line "Got 401, attempting token refresh and retry" is false. Nothing repairs the state: no code reads `subStatus` from a 401 body (`grep` finds it only in the token-grant logger at `:362`), `state` stays `Authenticated`, `session.isExpired` stays NO, so the Reconnect button stays hidden (`TidalPreferencesController.mm:448-452`) while Preferences reports "Token valid — expires in Xh". Every playbackinfo, metadata, search and sync call fails with "Authentication required" until the token naturally enters the refresh window. Trigger: server-side invalidation with local lifetime remaining (password change, sign out all devices, session limits, clock set back). The project's own design doc specifies the missing behaviour at `:204` and `:1324`; CHANGELOG.md:85 claims it already works.
**Counterargument (recorded, not decisive):** for the most common trigger TIDAL usually revokes the refresh token too, so a forced refresh would also fail — but it would then fail *truthfully*, populate `lastRefreshError`, and let the UI prompt re-auth instead of leaving a dead token looking healthy.
**Fix:** add a `force` flag (or a second handler) used by the 401 path so a refresh grant is actually posted; parse `subStatus` and force-refresh on 11003/6001/11001/11002/11101; on a second 401 transition state so the UI offers re-auth.
**Reference:** tidal-sdk-web `auth.ts` `knownSubStatus`; TIDAL `Auth.md`; music-assistant `api_client.py` (401 → forced refresh + one retry); kodi tidal2 `token_expired` (401 + subStatus 11003); tiddl `client.py` (refresh on any 401).

### Medium

**M1 — `immersiveaudio=false` is not sent and `audioMode` is never read**
`src/API/TidalAPI.mm:405`. The playbackinfo query is `?audioquality=…&playbackmode=STREAM&assetpresentation=FULL`. `grep` for `audioMode` / `immersiveaudio` in `src/` returns nothing. For a track whose album has an Atmos edition, TIDAL returns the immersive asset (observed as `audioQuality=LOW, audioMode=DOLBY_ATMOS, codecs=eac3, manifestMimeType=vnd.tidal.bts` by music-assistant PR #6244 and tiddl issues #359/#368) and `StreamResolutionPolicy` accepts it, caches it for 15 min and labels it "Normal (96 kbps)". Verification split: one verifier established that foobar2000 2.26 on macOS *can* decode E-AC-3 (FFmpeg `--enable-decoder=eac3`, `packet_decoder::owner_MP4_EAC3`), so the likely outcome is a silent lossy 5.1 downgrade rather than a broken track; AC-4 would fail outright. Not verified against this component's client ID (`fX2JxdmntZWK0ixT`). CHANGELOG.md:67 already claims Atmos tracks fall back to LOSSLESS; no code implements that.
**Fix:** append `immersiveaudio=false`; optionally parse `audioMode` and reject `DOLBY_ATMOS`/`SONY_360RA` so the cascade continues. One-line hardening either way.
**Reference:** music-assistant `streaming.py` ("never ask for the Atmos asset"); tiddl `downloader.py` (skips `audioMode == DOLBY_ATMOS`); kodi tidal2 `koditidal.py` (refuses AC4/360RA); tidal-sdk-android exposes `immersiveAudio` defaulting to true server-side.

**M2 — Reconnect destroys the persisted session on any transient refresh failure**
`src/UI/TidalPreferencesController.mm:599-603`. On `!success` — with no error classification, because the completion is `void(^)(BOOL)` — it calls `signOut` (→ `deleteAllTokens`, `SecItemDelete` on both tokens) then starts a fresh device flow. `TidalAPI.mm:347` maps every transport error to `NetworkFailure` and `:367` maps every non-200, including 429 and 5xx, to `TokenRefreshFailed`; `finishRefreshWithSession` deliberately defers the decision ("Don't signOut here", `:494-496`). The button is visible exactly when `state == Authenticated && session.isExpired`, which is reached after the proactive timer has been failing for >5 min — i.e. the outage that makes the user click is the outage that makes the refresh fail. `signOut` also cancels the 5-minute retry timer, converting a self-healing state into a terminal one, and the chained device-code request fails on the same dead network. Recovery is a full link.tidal.com pairing.
**Fix:** carry the `NSError` (or a terminal/transient flag) into the completion; wipe only on 400 `invalid_grant`/`unauthorized_client`/`invalid_request` and 401 `access_denied`/`invalid_client`; keep the session and retry with backoff otherwise.
**Reference:** TIDAL `Auth.md` (that exact five-code logout list; 5xx retried 5x with exponential backoff); strawberry `oauthenticator.cpp` (clears only on `invalid_grant`); music-assistant `_perform_refresh` (logs and returns False, credentials untouched).

**M3 — A failed startup refresh parks the service in Idle with a live session, and nothing re-enters Authenticated**
`src/Services/TidalAuthService.mm:132-142`. `loadStoredSession` installs the session on both the service and `JLTidalAPI` (`:126-127`) *before* deciding state; on refresh failure it sets `Idle` and never calls `scheduleProactiveRefresh`, so no retry timer exists. `finishRefreshWithSession` (`:462-502`) never touches `state`, so even a later successful transport-driven refresh leaves it Idle. `ensureValidTokenWithCompletion` (`:507-512`) and `isAuthenticated` (`:80-83`) gate on state alone, so browser, sync, album art and playback all refuse with "Not authenticated" while a valid refresh token sits in the Keychain. Preferences shows "Not signed in / Connect to Tidal" and hides Reconnect; the Connect button starts a full re-pairing. The proactive-timer path reaches the *opposite* state for the same failure, which is the tell that this is an oversight. Trigger: launch offline or during a network hiccup with a token inside the 300 s window. Recovery is an app restart, which nothing signposts. `JLTidalAuthStateExchangingToken` is declared and UI-handled but never assigned.
**Fix:** derive readiness from the session, not a parallel enum — on startup failure keep `Authenticated`-with-expired-token (or add a `NeedsRefresh` state), arm the existing 300 s retry, and have `finishRefreshWithSession` set `Authenticated` on success.

**M4 — Metadata failures are converted into fabricated tags instead of errors**
`src/Integration/TidalInputDecoder.mm:681-693` + `:708-719` (info reader), `:315-327` + `:523-543` (decoder). `TidalInfoReader::open` returns normally on abort, on the 5 s timeout and on any fetch error, leaving `m_trackInfo` nil; `get_info` then writes `TITLE = "Tidal Track <id>"`, `ARTIST = "Tidal"`. fb2k treats a reader that returns as a successful read and commits it. `get_file_stats` returns `filetimestamp_invalid`, so the core never re-reads on its own. The decoder path has the mirror problem: an 8 s metadata stall leaves `m_trackInfo` nil but still opens the stream, and `get_info` then publishes an overlay with no TITLE/ARTIST/ALBUM, which `input_helper`'s `hint_reader` commits for the playing item. Both are reachable without a slow link: a 429 completes immediately with an error (no retry, H4), and the limiter's backoff then pushes subsequent requests past the reader's 5 s cap. Practical damage concentrates on "Reload info" while offline, signed out or rate-limited, which overwrites good tags with placeholders. Returning normally on abort also violates `abort_callback.h:14`; the sibling `TidalAlbumArtExtractor.mm:73-80` throws correctly, so this is an inconsistency, not a convention.
**Fix:** throw `exception_aborted` on abort and an `exception_io` subclass on timeout/fetch error so the core keeps existing info; keep the placeholder only for a genuinely unparsable URL; in the decoder, do not publish an empty overlay when `m_trackInfo` is nil.

**M5 — Every imported track re-fetches `/v1/tracks/{id}` although the list response already carried it**
`src/Services/TidalStreamResolver.mm:253-263`. `metadataCache` has exactly one writer — its own API completion. Neither the browser nor the sync engine seeds it, though both hold fully parsed `JLTidalTrack` objects (sync even caches them in `cachedPlaylistTracks`, `TidalPlaylistSync.mm:356`) and then reduce them to `tidal://track/<id>` strings. fb2k opens `TidalInfoReader` per location, so a favorites pull of N tracks issues N authenticated GETs from the loader thread for data already in RAM — minutes for a real library, and the direct cause of M4 firing in bulk. The sibling Cloud Streamer component pre-caches for exactly this reason; the TIDAL port dropped that step. The design doc specified a network-free info reader (`docs/design/2026-01-07-tidal-integration.md:586`).
**Fix:** seed the resolver metadata cache (or a `metadb_hint_list`) from every list response before calling `process_locations_async`.

**M6 — 403 re-resolve restarts the inner decoder at 0:00; `seek()` has no handling at all**
`src/Integration/TidalInputDecoder.mm:505-506`, `:590`, `:605-609`. `tryReopen` assigns the new decoder and calls `initialize`, which per `SDK/input.h:73` resets to the beginning; `run()` then continues, so audio restarts while fb2k's position clock keeps counting from the old offset. `m_samplesDelivered` is accumulated at `:573` but used only for the premature-EOF log. The design doc specified `seek(savedPosition)` (`:474-475`) and `BACKLOG.md:14` already tracks it. Two aggravators the backlog entry does not cover: the retry gate is `strstr(msg, "403") || strstr(msg, "Forbidden")` on the *core's* exception text, which is not verified anywhere in the tree (the SDK defines no HTTP-status exception), so the path may be dead; and `seek()` — the operation most likely to issue a fresh signed request — delegates with no try/catch, so a post-expiry seek fails the track outright. BTS-only: `tryReopen` correctly gives up for DASH.
**Fix:** track decoded seconds (sum `p_chunk.get_duration()`, reset in `seek()`/`initialize()`), seek after `initialize()` when `can_seek()`, and fail the retry rather than restarting when it cannot; wrap `seek()` in the same re-resolve path; capture the reader's real exception text once and match on that.

**M7 — `remove_playlist`'s return value is ignored, and the component's own lock refuses the removal**
`src/Core/TidalPlaylistSync.mm:424-434`; `src/Integration/TidalPlaylistLock.mm:45-47`, `:83-85`. Every pull-created playlist gets `installSyncLock(newIdx)` (`:396`) whose `query_playlist_remove()` returns false with `filter_remove_playlist` in the mask. `removeSyncLock` exists in the header and has zero callers (verified by grep). A later pull that plans that playlist's deletion calls `remove_playlist`, the core refuses, the playlist stays — yet the uuid/name mapping is dropped unconditionally and the report counts it "removed". Subsequent previews re-propose the same Delete forever, and push now sees an unmapped `TIDAL » …` playlist and plans a Create, duplicating it remotely. Bounded to the session that created the playlist (locks are not persisted or reinstalled at startup), which is why this is medium rather than part of H1.
**Fix:** call `removeSyncLock(idx)` first, check the `bool`, and only drop the mapping and count the change when it returned true.

**M8 — DASH segment count is exact only when exactly one `<S>` carries `r>0`**
`src/Core/ManifestParser.mm:82` (`count += (r > 0) ? r : 1;`), `:217` (`segCount = 1 + 1 + …`). Per the DASH spec each `<S>` yields `r+1` segments, so the correct URL count is `1 + Σ(r_i + 1)`; this formula produces `2 + Σr + k0`, i.e. one too many when no `<S>` has `r>0` and one too few when two or more do. The formula is a verbatim port of python-tidal's `DashInfo.get_urls`, and tidal-dl-ng — which uses the same list — carries an explicit tolerance with the comment that "for tracks < ~8 s the last URL is invalid (HTTP Error 500) and not necessary". With ~4 s segments, "no `<S>` with `r>0`" is exactly "track under ~8 s". `TidalDashCache.mm:236-240` then discards the whole assembly on that one failed GET and `TidalInputDecoder.mm:362` throws, so sub-8-second tracks (intros, skits, interludes) fail deterministically with DASH on by default. `Tests/ManifestParserTests.mm:99-102` pins the over-count (`<S r="0"/><S/><S/>` → 5, spec says 4). The multi-run under-count is spec-derived only; no evidence TIDAL's packager emits it.
**Fix:** `count = 1 + Σ(r_i + 1)` (tiddl's formula; identical to today's for the common `<S r=N/><S/>` shape), re-pin the test to 4, and relax the `segCount > 2` gate at `:226` so a legitimate two-URL manifest is not rejected. Optionally tolerate a failure on the final URL as tidal-dl-ng does.

**M9 — DASH assembly has no per-segment retry and no re-resolve on 403**
`src/Integration/TidalDashCache.mm:38` (`dashSyncGET` collapses every non-2xx and every transport error to nil, status logged but not returned), `:236-240` (one nil segment discards the whole partially assembled blob). A hi-res track needs dozens of sequential GETs; one timeout at segment 60 throws away 45 MB and the track is skipped. Because the status is not propagated, the caller cannot distinguish an expired signature (403 → should re-resolve and invalidate `StreamCache`) from a 503 (→ should retry). `tryReopen` explicitly bails for DASH, and it is only reachable from `run()`, never from `open()`. Partly mitigated in sequential playback: a failed assembly is not cached, so the decoder's later open re-downloads from scratch — an implicit second attempt that first-picked, shuffled and manually clicked tracks do not get.
**Fix:** retry each segment (3 attempts, backoff) on network error/5xx/429; return the status so a 403/410 triggers `invalidateCacheForTrackID` + one re-resolve; consider resuming from the failed index.
**Reference:** tidal-dl-ng mounts `Retry(total=5, backoff_factor=1)` per segment; TIDAL Player spec requires a fresh playbackinfo fetch ("handbrake") when a sub-resource returns 4xx.

**M10 — Whole-track in-memory DASH assembly with a 1 GB hard cap**
`src/Integration/TidalDashCache.mm:229`, `:242-246`; budget comment at `:10-13`. The "~50-75 MB each" sizing is for roughly 24/48; 24/192 FLAC runs ~40 MB/min, so a 10-minute track is ~400 MB and anything over ~26 minutes exceeds the cap, is downloaded in full, discarded, and fails with no fallback to a lower tier (`StreamResolutionPolicy` only downgrades at resolve time). Below the cap, the playing blob is retained by the decoder's `MemoryFile` while the prefetcher assembles the next one, so the 320 MB LRU cannot bound peak RSS. Every reference player streams instead: music-assistant serves the MPD on a local route and lets ffmpeg fetch segments, mopidy-tidal writes the MPD for GStreamer's dashdemux, kodi routes to inputstream.ffmpegdirect/adaptive. Only the downloaders assemble whole tracks.
**Fix:** long term, feed the inner decoder through an on-demand segment-fetching `file` implementation with read-ahead. Short term, estimate size from duration/bitrate and fall back to the next lower tier instead of failing.

**M11 — v1 mutations are POSTed as JSON; every working client sends form-encoded**
`src/API/TidalAPI.mm:1146-1153` is the only body path and always sets `application/json`. Callers: favorites add (`:710`), playlist create (`:848`), playlist items add (`:879-883`). The OAuth calls in the same file already use `JLTidalOAuthFormBody` with `x-www-form-urlencoded` (`:191`, `:261`, `:334`), so the helper exists and is simply not wired in. A survey of ~20 independent v1 clients (python-tidal, music-assistant with an explicit `as_form=True` for exactly these three calls, lms, kodi tidal2, strawberry, and a client replicating listen.tidal.com's own DevTools headers) found no working client that sends JSON here. If a v1 endpoint binds request parameters, the JSON body is ignored: the playlist is created with a default title, the items POST 400s, and `HTTPResponsePolicy.mm:80-84` surfaces an opaque "Unexpected status: HTTP 400" with the body discarded. Push then fails after the remote playlist already exists, and the favorites context menu prints "Added N tracks" before the request completes (`TidalBrowserController.mm:2101-2114`), so a failure there is invisible. `BACKLOG.md:12` records push sync as untested against the real API.
**Fix:** add a form-encoded body option to `requestWithURL` reusing `JLTidalFormEncode`, use it for those three calls, verify once live and record the result in `docs/`. Consider kodi's 500-ids-per-POST chunking with a fresh ETag per chunk.

**M12 — The v2 folders request and parser match no documented response shape, so folder hierarchy has never worked**
`src/API/TidalAPI.mm:1004-1021`; `src/Core/ResponseParser.mm:163-164`; `src/Core/TidalModels.mm:296`, `:302-306`. The request is `GET {listen.tidal.com/v2}/my-collection/playlists/folders` with no `folderId`, `includeOnly`, `limit` or `cursor`. Every reference client sends `folderId=root&limit=50&includeOnly=FOLDER|PLAYLIST` and pages by the response `cursor`; children require a second request with `folderId=<id>`. The listing is flat and items carry `trn`, `name`, `parent` (object) and `data{…}` with the discriminator `itemType` — this parser reads a top-level `type`, expects children nested under `items`, and reads a non-existent `parentFolderId`. Either the parameterless request errors (logged at debug only, `TidalPlaylistSync.mm:103-110`) or it returns 200 and `foldersFromItems` yields an empty array; either way every pulled playlist gets the flat `TIDAL » title` name. The unit fixture (`Tests/ResponseParserTests.mm:129-146`) is hand-written in the wrong shape, giving false assurance. Secondary hazard: because pull identity is name-based, fixing the parser alone converts every foldered playlist into a Create+Delete pair.
**Fix:** rewrite to `folderId=root&limit=50&includeOnly=FOLDER` (then per-folder `includeOnly=PLAYLIST`), follow `cursor`, read `itemType`/`trn`/`name`/`parent.id`/`data.uuid`, build the tree client-side, and pin the parser against a captured live response. Plan the one-time rename migration deliberately.

**M13 — ISRC resolution uses free-text search instead of the ISRC filter endpoint**
`src/API/TidalAPI.mm:1030-1033` builds `/v1/search/tracks?query=<ISRC>&limit=5` with the comment "Use search API with ISRC as query (v1 approach)", then exact-matches client-side (`ResponseParser.mm:181`). No reference client resolves ISRC through text search: python-tidal and music-assistant both use `GET https://openapi.tidal.com/v2/tracks?filter[isrc]=…` with the same Bearer token, and the official OAS documents `filter[isrc]` on `/tracks`. TIDAL staff stated in 2023 that ISRC lookup was not possible before that endpoint existed; FreeYourMusic's matching docs list TIDAL as not ISRC-searchable. With `limit=5` over a relevance ranking, a real match ranked sixth is dropped anyway. Consumed by push sync for every non-`tidal://` local track (`TidalPlaylistSync.mm:758`); misses are `logDebug` only and the track is silently omitted while push reports success. The advertised "ISRC Track Matching" feature (CHANGELOG.md:106) is very likely non-functional.
**Fix:** call `GET https://openapi.tidal.com/v2/tracks?countryCode=XX&filter[isrc]=…` with `Accept: application/vnd.api+json`, read `data[].id`, keep the exact-ISRC post-filter, and fall back to the search heuristic only if the openapi call is rejected for this client.

**M14 — The ETag probe bypasses the request pipeline, and push Create swallows its failure**
`src/API/TidalAPI.mm:963-1001`; `src/Core/TidalPlaylistSync.mm:547-549`. `getPlaylistETagForID` builds a raw `NSURLSession` request: it checks only `session.isValid` (never invoking `tokenRefreshHandler`), sets only `Authorization`, injects no `countryCode`, ignores the rate limiter's current delay, skips `JLTidalHTTPResponsePolicy`, and maps every non-200 — 401, 429, 5xx alike — to a generic `InvalidResponse "HTTP %ld"`. It is the one request in the push flow with the weakest handling, and it runs immediately after a side-effecting `createPlaylist`. On a nil ETag the Create branch calls `dispatch_group_leave` with no `firstError`, no log, and no uuid/name mapping recorded — so the run reports "Push complete", an empty playlist sits on the TIDAL account, and the next push plans another Create, duplicating it. The Update path (`:860-864`) propagates `etagError` correctly, which makes this an oversight rather than a design choice. The realistic trigger is a 429 (the flow fans out ISRC lookups 4-wide and creates concurrently) or a transient network error, not token expiry.
**Fix:** extend `performRequestWithURL` to hand back the `NSHTTPURLResponse` and route the probe through it; record `etagError` in `firstError`; store the name↔UUID mapping as soon as `createPlaylist` succeeds, as the zero-tracks branch already does.

**M15 — No client-side request pacing: push apply, favorite-album fill and browser favorite mutations fan out one request per item**
`src/Core/TidalPlaylistSync.mm:511` (unbounded loop over changes), `:811-828` (favorite albums), `src/UI/TidalBrowserController.mm:2107`/`:2124` (one POST/DELETE per selected track). The same file already uses `dispatch_semaphore_create(4)` for pull track fetch (`:153`) and ISRC lookup (`:753`), so the pattern is known and simply not applied. `JLTidalAPI` gates only on the reactive limiter, which is zero until a 429 has already landed, and a 429 is not retried — so a single one turns a whole push into "push failed" after some playlists were already created remotely. Fan-out is worse than it looks: `pushChangeForName` marks every mapped playlist as Update without diffing, and each one creates its own 4-slot ISRC semaphore, so N playlists can mean 4N concurrent searches. `NSURLSession` will not serialise it — the API session sets no `HTTPMaximumConnectionsPerHost` (unlike the art and DASH sessions) and TIDAL negotiates HTTP/2.
**Fix:** one global pacer in `JLTidalAPI` (token bucket ~4 req/s or 3-4 in-flight); reuse the existing semaphore in `applyPush`/`fetchAndApplyFavoriteAlbums` meanwhile; batch favorite adds (`trackIds` already accepts a comma list).
**Reference:** music-assistant `ThrottlerManager(rate_limit=4, period=1)`; strawberry 3 concurrent per queue behind a 200 ms flush timer; lms caps 10 pending metadata lookups; tidal-dl-ng sleeps 3-5 s between items.

**M16 — Every 403 becomes "Subscription required" and drives the full downgrade cascade; the response body is discarded**
`src/Core/HTTPResponsePolicy.mm:68-71`; `src/API/TidalAPI.mm:1208-1210`. The policy signature takes only status and `Retry-After`, so discarding `{status, subStatus, userMessage}` is structural. `StreamResolutionPolicy.mm:65-70` retries a lower tier on exactly this code, and with the default `HI_RES_LOSSLESS` preference a persistent 403 costs five playbackinfo requests per attempt — uncached, since only successes are stored, and repeated by the prefetcher. The user sees "Subscription required" for a geo-block, a quota, or a forbidden playlist mutation. Note the cascade's premise is contradicted by this project's own finding in commit `3fa7075`: TIDAL answers an unavailable tier with 200 + HIGH, not 403, so a real 403 is almost never a tier problem.
**Fix:** parse `status`/`subStatus`/`userMessage` from every non-2xx body into `userInfo`; cascade only for the subscription sub-status; propagate the rest immediately with the server's message; log `userMessage` always.
**Reference:** tidal-sdk-web `getErrorId` (4010 quota, 4032/4035 location, 4033 subscription) with no quality retry; kodi tidal2 shows status + `userMessage` without cascading.
(The v2 `CONCURRENT_PLAYBACK` code cited in the original finding does not apply — this component calls the v1 endpoint.)

**M17 — A folder-fetch failure silently degrades to flat naming, turning a transient v2 error into a mass Create + Delete plan**
`src/Core/TidalPlaylistSync.mm:101-110`: on error the folder fetch logs at *debug* level (off by default) and substitutes `@[]`. Names derive from `playlistFolderPaths`, so every foldered playlist is renamed `TIDAL » X`, and `planPullPreview` then proposes Delete for every local `TIDAL » Folder » X` name absent from the remote-derived set (`:336-348`); only `failedUUIDs` and favorites errors are protected. This contradicts the module's own stated policy three lines below at `:112-113` ("A failed fetch is recorded, never treated as an empty collection — that would destroy the local playlist") and the policy established in commit `5016697`. Delete+Create loses local ordering and any non-tidal items; the next successful pull reverses it, so playlists thrash. Mitigated by the confirmation dialog, which lists every change.
**Fix:** treat a folder-fetch failure as fatal for the preview (like `playlistsError`), or at minimum protect every local name whose folder segment cannot be verified, and log at error level.

**M18 — Playlist identity is split across two unreconciled stores**
`src/Core/TidalPlaylistSync.mm:397-403` (Create writes both maps), `:408-420`/`:438-439` (Update and Unchanged write neither), `:409`/`:424` (pull matches by name), `:486` + `SyncPlanner.mm:272-284` (push resolves only through the map, Create whenever the uuid is absent), `:930-935` (the map lives in `~/Library/Application Support/foobar2000-v2/`, while the fb2k v2 profile documented in `docs/hidden-options.md:7` is `~/Library/foobar2000-v2/`). Because pull records the mapping only on Create, and pull never Creates while a same-named local playlist exists, a lost map entry is permanent: every pull reports Unchanged and every push proposes a full remote duplicate. Copying or restoring the fb2k profile to a new machine does exactly that — the map file is in a different tree and does not come along. Push never deletes, so duplicates accumulate. Gated by the push confirmation dialog, which lists each "Create:" line without indicating the name already exists remotely.
**Fix:** one identity anchor — store the TIDAL UUID as a persistent playlist property (`playlist_manager_v2::playlist_set_property`, `SDK/playlist.h:409-416`) and read it in both pull snapshot and push preview, so identity survives renames and profile moves. Minimum: reconcile the map on Update/Unchanged, treat an unmapped `TIDAL » …` playlist as adopt-not-create, and move the file under `core_api::get_profile_path()`.

**M19 — `applyPull` has no failure path and reports the plan, not the outcome; the UI re-arms during the import**
`src/Core/TidalPlaylistSync.mm:376-447`, `:620` (`on_aborted` empty), `:805`/`:834` (`completion(YES, nil)` unconditionally, with `getAlbumTracksForAlbumID` errors ignored at `:815-826`); `src/UI/TidalBrowserController.mm:2304-2305` (both sync buttons re-enabled when the *preview* returns), `:2329` (prints the pre-apply plan summary). In the common case `completion(YES,nil)` runs in the same main-thread block that just queued the imports, so "Pull complete: 3 new" is displayed over still-empty playlists — and the import is network-bound per track (M5), so the window is seconds to minutes. Pull is clickable again immediately: a second preview taken inside that window snapshots the not-yet-populated playlist as 0 tidal items, plans an Update, and its apply does `playlist_clear` plus a second `process_locations_async`; when both notifies land the playlist holds every track twice. Because the planner diffs *sets* of track IDs, a doubled playlist then diffs as Unchanged forever. A favourite-album playlist created empty because its fetch failed is likewise Unchanged forever (`SyncPlanner.mm:243-260` tests existence, not count) — permanent, unrepairable through the UI, and reported as success.
**Fix:** make apply an operation with a result — count create/import failures, implement `on_aborted`, wait for all import notifies (dispatch group) before calling completion, and report the outcome. Carry per-playlist track lists in the report object rather than the singleton's `cachedPlaylistTracks` (written on a global queue, read on main). Keep both buttons disabled from preview start to apply completion and reject a new preview while an apply is in flight.

**M20 — `on_quit` does not stop background work; late completions re-enter `configStore`, which bug-checks rather than throws**
`src/Integration/Main.mm:74-88`; `src/Core/TidalConfig.mm:19-27`; `src/Services/TidalStreamResolver.mm:20`, `:149`. The three `shutdown` calls flip flags and clear caches but join nothing: no `invalidateAndCancel` exists anywhere in `src/`, and the resolver's playbackinfo completion reads `TidalConfig::isDASHEnabled()` twice on the URLSession thread. `fb2k::configStore::get()` is `std_api_get` → `_standard_api_get_internal` → `uBugCheck()` (`SDK/service.cpp:66-68`), i.e. `pfc::crashImpl()` — a null write, not an exception — so the `is_valid()` checks and `catch (...)` in `TidalConfig` are dead code for the service-gone case. The developer has hit this class before (commit `3ae4387` fixed a shutdown crash from `configStore` access in a static destructor) and hardened several neighbours (`StreamCache::m_shutdown`, the cached debug flag, the null log backend, DashCache's late-assembly re-check) — this one read was missed. The window is narrow (quit within ~1 s of a track change or during a library save, with the response landing after service teardown) and the consequence is a crash report at exit.
**Fix:** snapshot `dashEnabled`/quality before issuing the request and pass them into the completion (or cache them in an atomic like the debug flag already is); `invalidateAndCancel` the API session in `on_quit`; `configStore::tryGet` + `core_api::are_services_available()` as a belt.
Noted as refuted within this: the log-backend race is harmless (`console::print` is gated on `are_services_available()`), and DashCache assembly does cancel cooperatively.

**M21 — Release dates are parsed in the local time zone and formatted in UTC**
`src/Core/TidalModels.mm:12-21` (`sharedDateOnlyFormatter` sets no `timeZone`, so `dateFromString:` yields local midnight), `:130`/`:139`/`:209`; `src/Integration/TidalLibrarySaver.mm:383-392` and `src/Core/LibraryLayout.mm:70-80` both pin GMT+0. Reproduced with a standalone Foundation program using the exact production configurations: under Europe/Prague (this machine) `2024-01-01` → saved `date` tag `2023-12-31` and year folder `2023`; `2024-07-15` → `2024-07-14`. Correct under UTC and west of it. So every FLAC/M4A written by Save to library carries a date one day before TIDAL's, 1-January releases land in a `[YYYY-1]` folder, and the tag disagrees with the DATE fb2k shows for the same track streamed (the decoder's formatter is local and consistent). `Tests/LibraryLayoutTests.mm:16-22` masks it by building its fixture date with an explicit UTC formatter instead of the production parser.
**Fix:** pin one fixed zone across all three sites (release dates are calendar dates, not instants) — or carry the raw `yyyy-MM-dd` string alongside the `NSDate` and emit that. Fix the test helper to go through the production parser.

**M22 — Replay gain is downloaded twice per play and discarded**
`src/Integration/TidalInputDecoder.mm:523-543`; `src/Core/TidalModels.mm:333-382`, `:42-156`. `grep -rniE 'replaygain|peak|loudness'` over `src/`, `Tests/` and `docs/` returns only unrelated hits. Both endpoints the component already calls carry the data — playbackinfo has `trackReplayGain`/`trackPeakAmplitude`/`albumReplayGain`/`albumPeakAmplitude`, `/v1/tracks` has `replayGain`/`peak` — and `file_info::set_replaygain` is right there in the SDK (`file_info.h:111`). With fb2k ReplayGain processing enabled, local files are normalised and TIDAL streams are not, so mixed playlists jump in level; TIDAL's own clients default to `loudnessNormalizationMode: 'ALBUM'`. The inner FLAC/MP4 decoder cannot rescue this because TIDAL's BTS and DASH payloads carry no tags.
**Fix:** parse the four playbackinfo fields (fallback `replayGain`/`peak` from `/v1/tracks`) into `JLTidalPlaybackInfo` and call `p_info.set_replaygain()`; have `TidalInfoReader` set track gain from the metadata call so the playlist column works before playback.

**M23 — `allowStreaming` / `streamReady` are never parsed**
`src/Core/TidalModels.mm:42-156`; `grep` returns zero hits anywhere in `src/` or `Tests/`. Region-restricted, withdrawn or not-yet-released tracks are listed normally, given a quality badge from stale `audioQuality`, pulled into local playlists by sync, and only fail at play — as a 404 (one request, "Track not found") or a 403 (five playbackinfo requests down the cascade, then "Subscription required"). Failures are not negatively cached, so the cost repeats on every play attempt and again on every prefetch. Every reference client gates on these flags: strawberry skips the song, lms drops the entry, kodi computes `available = streamReady and allowStreaming`, tiddl refuses, python-tidal exposes both and only parses `mediaMetadata` when available.
**Fix:** parse both into `JLTidalTrack`/`JLTidalAlbum`; dim or mark unavailable rows; short-circuit in the resolver before the first playbackinfo request. Do not silently drop them from the pull diff — that makes the local playlist stop mirroring the remote one.

**M24 — Track responses carry a thin nested album, so ALBUM ARTIST and TOTALTRACKS are never emitted and DATE is the stream start date**
`src/Core/TidalModels.mm:114-141`. `JLTidalTrack` reads `album[@"artist"]`, `album[@"numberOfTracks"]` and `album[@"releaseDate"]` from the *track* response's nested album, which in v1 carries only `{id, title, cover, vibrantColor, videoCover}` — python-tidal's `Album.parse` documents this ("If the album is created from a media object, this object will only contain the id, name, cover and video cover") and offers `session.track(id, with_album=True)` precisely to fetch the real one. `/v1/albums/{id}` is never requested anywhere in this component (the only album URL is `/v1/albums/%@/tracks`). So `_albumArtist` stays nil, `_totalTracks` stays 0, and `_releaseDate` always falls through to `streamStartDate` — the date TIDAL ingested the asset, not the release date. Commit `8a9a5b8`'s "track-level releaseDate fallback when album doesn't provide one" is evidence the album date was already observed missing. Consequences: fb2k's album-artist grouping splits compilations; the CHANGELOG's "TOTALTRACKS in track metadata" claim cannot be met from this endpoint; DATE is wrong for all back-catalogue and that wrong year is baked into export folder names; and because `TidalLibrarySaver.mm:112-113` falls back to the performing artist, `isVariousArtists` almost never fires and a VA compilation exports as N single-track folders.
**Fix:** fetch `GET /v1/albums/{album.id}` once per album, cached by album id alongside track metadata, and take `artist.name`, `releaseDate`, `numberOfTracks`, `numberOfVolumes` from it; keep `streamStartDate` only as an explicit last resort. For browser "add album" and favourite-album pulls the `JLTidalAlbum` object is already in hand and can be merged with no extra request.

**M25 — All API traffic shares one `NSURLSession` whose completions are delivered on a single serial queue, and blocking work runs on it**
`src/API/TidalAPI.mm:127-130` creates the session with no `delegateQueue`, which was confirmed empirically on this machine (`maxConcurrentOperationCount == 1`, four 1 s completions ran strictly sequentially). On that one queue: `finishRefreshWithSession` → `storeSession:` → two `SecItemDelete` + `SecItemAdd` pairs plus NSUserDefaults writes; the resolver's playbackinfo completion → base64 + regex over the MPD, two `configStore` SQLite reads, and an unconditional 4 KB console dump of the manifest. The one consumer that cannot tolerate a stall is the decoder's resolve wait at `TidalInputDecoder.mm:266-270`, which has *no* timeout at all, unlike the metadata wait (8 s), the reopen wait (10 s), the info reader (5 s), album art (10 s) and the library saver (30/60 s). Two sync loops (`TidalPlaylistSync.mm:156`, `:756`) wait `DISPATCH_TIME_FOREVER` on signals delivered from that same queue, and the comment at `:153-155` asserts deadlock-freedom without noting the queue is serial. The routine per-completion cost is a few ms — the pagination path touches none of the expensive work — so this is a structural hazard plus one concrete defect rather than a steady-state performance problem.
**Fix:** give the decoder's resolve wait the same finite cap its siblings have (highest value, smallest change); hop each completion onto a private queue as its first statement, or give the session a concurrent `delegateQueue`; snapshot config values before issuing the request; gate the manifest dump on debug logging.

**M26 — Browser: an artist-albums error is rendered as "no albums", and Back then re-runs the same failing fetch**
`src/UI/TidalBrowserController.mm:1290-1295`, `:1310-1316`, `:970-979`; `src/Core/BrowserLogic.mm:88-95`. `if (error || albums.count == 0)` collapses a 401/429/5xx/offline failure into the empty-catalogue fallback, and `finishLoading`/the status label never see the error. `loadArtistTopTracks` enters `ArtistTopTracks` with `currentArtist` still set and a comment asserting "there is no artist-albums level to return to", while the tested `BrowserLogic` rule returns YES for exactly that state — so Back calls `drillIntoArtist:` again. For an album-less artist (the case the fallback was written for) that re-fetches, gets zero again, and lands on Top tracks again: Back is permanently non-functional, and the tooltip advertises a destination it can never reach. The only exits are changing panel mode, search type, or typing a new query. Related, same file: drill-down, artist and playlist completions carry no `searchGeneration` guard, unlike the search and library loaders, so a late drill-down completion can overwrite the list currently displayed under a different breadcrumb (`:1255-1273`, `:1287-1306`, `:1319-1335`, `:1349-1368`).
**Fix:** separate the two states — on error, show the error and stay put; only an empty *success* falls back. When falling back, clear `currentArtist` (so Back routes to the root) or add an explicit `topTracksIsRoot` flag to the `BrowserLogic` predicate with a unit test. Apply the generation guard uniformly by routing every completion through one "present results for (mode, generation)" helper.

## 4. Refuted but notable

Findings that verification rejected, with the reason — listed because several are near-misses you may still want to know about.

- **`signOut` has no fan-out** (stream/blob/metadata caches and the sync map survive sign-out). Rejected: the caches are keyed by track and are not user-scoped; an account switch re-resolves through a fresh token, and no path serves another account's data.
- **Decoder candidate loop swallows every `std::exception`.** Rejected: HEAD commit `e79340d` already changed this to try every candidate and rethrow the first failure; the behaviour described was the pre-fix state.
- **Input registers as a redirector without `flag_redirect`.** Rejected: the SDK does not require it for this pattern on macOS, and inner-decoder selection by extension/MIME works as intended.
- **Pagination infers completeness from page length and discards `totalNumberOfItems`.** Rejected: `PaginationPolicy` stops on a short page, which is correct for every endpoint in use; a server-clamped `limit` would have to differ from the requested one, which was not demonstrated.
- **Device-code polling ignores RFC 8628 `slow_down`.** Rejected as a real-world defect: TIDAL's device endpoint was not shown to emit `slow_down`, and the fixed 5 s interval is at or above the returned `interval`. (music-assistant does handle it — cheap to add if you touch that code anyway.)
- **MemoryFile advertises a FLAC content type for an fMP4 blob and does not report `is_in_memory()`.** Rejected: the decoder candidate list is driven by URL extension with an explicit fallback, so the content type is advisory; no observed mis-selection.
- **Album art extractor reports timeouts and signed-out state as `exception_album_art_not_found`.** Rejected: that is the documented "no art here" signal; the core simply moves to the next extractor. No user-visible harm.
- **DASH manifest variants (`@duration`, `$Time$`, `startNumber`, `initialization`) unsupported.** Rejected: TIDAL's packager emits only the `$Number$` + SegmentTimeline shape; the real defect in that area is the count formula (M8), which is confirmed.
- **Keychain `storeValue` is delete-then-add, so a failed `SecItemAdd` loses the stored token.** Rejected as a practical defect: `SecItemAdd` of a freshly deleted generic password by the same code identity does not fail in the field; no observed loss.
- **Preferred-quality config value crosses the trust boundary unchecked.** Rejected: the value is written only by the preferences popup from a fixed table; an out-of-range value requires hand-editing `config.sqlite` with fb2k quit.
- **Missing `@autoreleasepool` on fb2k worker threads.** Rejected: fb2k's own worker threads and the decode thread drain their pools per iteration; no accumulation was demonstrated.
- **The shipped device-flow client cannot obtain HI_RES_LOSSLESS.** Rejected: python-tidal's claim concerns its PKCE path; this client's live behaviour (per commit `3fa7075`'s logs) returns lossless tiers normally.
- **`countryCode` falls back to the Mac's locale region with no `/v1/sessions` lookup.** Rejected as a defect: the token response's `user.countryCode` is used when present and the locale is only a last resort; strawberry does the same.
- **Assembled DASH blobs are cached without validation.** Rejected as written — but note H2 is the real version of this concern (wrong *key*, not missing validation).
- **MPD attribute values used without XML entity decoding.** Rejected: TIDAL's signed segment templates do not contain entities; no observed instance.
- **Library saver reads `__block` pointers after a semaphore timeout.** Rejected: the timeout path returns before any read that could race, and the feature is behind a hidden flag.
- **Sync apply blocks the main thread with `dispatch_sync` onto the state queue carrying the archive write.** Rejected: the archive write happens outside that block; the `dispatch_sync` protects only dictionary mutation.
- **Every track change couples the main thread to background queues via `dispatch_sync`.** Rejected: the prefetcher's main-thread work is a bounded playlist read; the resolve is async.
